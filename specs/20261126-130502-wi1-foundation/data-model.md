# Data model: WI-1 Foundation (Phase 1)

**Sources**: umbrella spec section 2.5, P-03, P-03a, FR-012, FR-013 to FR-017, FR-023, FR-024, FR-028, FR-045, FR-051; `research.md` R-07, R-08, R-18. **Database**: PostgreSQL 17, schema in `apps/server/src/db/schema.ts` (Drizzle), versioned SQL in `apps/server/drizzle/` generated by `drizzle-kit generate`, applied at start-up under `pg_advisory_lock` (FR-024).

## Conventions

- Closed sets are `text` with a `CHECK (... IN (...))`, never PostgreSQL enums (R-08): removing a value is one migration.
- Ids are `uuid`. Timestamps of rows are `timestamptz` set by the database. Legacy timestamps that the rules compare as strings (`updated`, `at`) stay strings inside `jsonb`, because the import skip rule compares them as strings (`ex.updated >= c.updated`, `archui.js:249`). Every save rewrites `updated` (`archui.js:38`), so only paths that do not save (read, export, an import entry that is skipped) must give the same string back, and a test pins that.
- Invariants live in the database where a constraint can express them; the rest are enforced by the single writer of each table (`PgCharacterStore.apply` for the character tables, `LlmGateway` for `llm_calls`, `SettingsService` for `settings`) and proven by the shared contract suite (FR-050).
- WI-1 writes only `characters`, `character_versions`, `llm_calls` and `settings`. The other tables are created now because FR-024 and AM2-09 require it, with only the columns the spec names; WI-2, WI-3 and WI-7 add columns by additive migrations.

## Tables written in WI-1

### `characters` (the current record of each character)

| Column | Type | Constraint | Source |
|---|---|---|---|
| `id` | `uuid` | primary key | FR-017 |
| `legacy_id` | `text` | null allowed; `CHECK (legacy_id IS NULL OR legacy_id <> '')` | FR-017 (`c_…`, `f_…`) |
| `version` | `integer` | not null, `CHECK (version >= 1)` | P-03 |
| `revision` | `bigint` | not null, `CHECK (revision >= 1)` | P-03 (optimistic concurrency only) |
| `data` | `jsonb` | not null; `CHECK (jsonb_typeof(data) = 'object' AND NOT (data ?| array['id','legacyId','version','revision','versions']))` | FR-013 |
| `seq` | `bigint` | identity, not null, unique | insertion order, the one order of `list()` (review V1) |
| `archived_at` | `timestamptz` | null allowed | FR-023 soft delete |
| `created_at` | `timestamptz` | not null, default `now()` | row bookkeeping |
| `updated_at` | `timestamptz` | not null, default `now()` | row bookkeeping |

- `data` holds the record of FR-013 without the four keys the columns own and without the legacy inline `versions`. The store composes the full record on read (`{ ...data, id, legacyId, version, revision }`). The CHECK makes a second copy of those keys impossible, so the columns are the only source.
- **One order.** `list()` returns characters by `seq`, the order in which they were first stored; an import, the pack and the seed insert in the order of their source arrays. This matches the legacy order within a session: `ARCH.chars` gains new characters with `push` (`archui.js:39`), and the export (`archui.js:211`) and the generator's crew list (`archfuturo.js:71`) iterate it as it is. After a reload the legacy order is IndexedDB key order, the order of the legacy id strings (`getAll`, `archui.js:25`), which uuids cannot reproduce. That difference is a parity row (FR-100), and the FR-050 suite asserts the `seq` order on both stores.
- No index beyond the primary key and the unique `seq`: the archive holds hundreds of rows (58 seeded), and every list reads all non-archived rows.
- Names are not unique (edge case "several characters share a name", `archui.js:209`).

### `character_versions` (immutable snapshots of superseded versions)

| Column | Type | Constraint | Source |
|---|---|---|---|
| `character_id` | `uuid` | not null, foreign key to `characters(id)` `ON DELETE RESTRICT` | P-03 |
| `version` | `integer` | not null, `CHECK (version >= 1)` | the superseded version's number (`v: old.version`, `archui.js:37`) |
| `version_at` | `text` | null allowed | that version's `updated` (`at: old.updated`, `archui.js:37`); null only for imported inline versions without `at` |
| `reason` | `text` | null allowed | reason of the save that superseded it (`why`, `archui.js:37`); FR-016 lists the four stored values; imported inline rows keep their own `why` |
| `data` | `jsonb` | not null, same CHECK as `characters.data` | the snapshot; it has no `revision` (the API types it `CharacterSnapshot`) |
| `created_at` | `timestamptz` | not null, default `now()` | row bookkeeping (2.5: "with `reason` and `created_at`") |
| primary key | | `(character_id, version)` | version numbers never reused (`archui.js:37`) |

- A row is written only by a **versioned save** over an existing character (P-03) and never updated afterwards: US1 scenario 3, "no existing row is rewritten".
- **Retention**: after each versioned save `PgCharacterStore.apply` deletes, in the same transaction, the rows of that character beyond the 15 highest versions (`.slice(-15)`, `archui.js:37`). The current version lives in `characters`, so the archive keeps 15 prior plus the current one (C9). Version numbers grow, so "highest" equals the legacy's "last by array order" for every row the store writes; the only rows that could differ are imported inline versions, which `planImport` normalises first (below).
- **Imported inline versions** (edge cases; review I6). The legacy keeps a file's `versions` array as it is (`Object.assign(archBlank(), c)`, `archui.js:249`), duplicates and odd numbers included. Before writing, `planImport` keeps only rows whose `v` is an integer in `[1, version - 1]`, deduplicates by `v` keeping the last occurrence in array order, and keeps the last 15 in array order. Without this a duplicate `v` would break the insert and a `v` equal to the current version would make the next versioned save collide forever. The difference is a parity row, and a test covers duplicate, out-of-range and non-integer `v`.
- `ON DELETE RESTRICT`: there is no hard delete in v1 (FR-023); a hard delete attempted by mistake fails instead of cascading.
- A deceased or disabled character keeps its history; a soft-deleted one keeps it too but is never listed (FR-023).

- Rows refused before the provider is called (rate limit, spend cap, invalid request) are never inserted: the table records calls, and the limits count calls (FR-028 "every call inserts one row when it starts"). The admission is one transaction under `pg_advisory_xact_lock(<rate key>)`: count the rows started in the last 60 s (in flight included), sum today's `cost_usd`, and insert the `in_flight` row only when both are under their caps (review I7). Concurrent requests at cap minus one therefore cannot all pass, and a refused request never fills the window it waits on. The spend sum does not include the cost of calls still in flight, so the cap can be overshot by at most the 6 calls in flight (L-01); `docs/security.md` says so.
- At start-up, rows still `in_flight` become `aborted` with `finished_at = now()` (FR-028).
- Privacy: the rows are kept until the player removes the database volume, as the security document says (spec FAQ).

**Required keys.** Only the nine keys of the contract sketch are required: `schema`, `id`, `version`, `revision`, `updated`, `name`, `sex`, `age`, `status`. Every other key is optional and typed when present; the record never invents a missing key, so it round-trips exactly as stored. `CharacterInput` leaves out `id`, `legacyId`, `version`, `revision` and makes `updated` optional; `CharacterSnapshot` leaves out `revision`. Derive JSON Schema for routes and documents from the constants core exports (`CHARACTER_JSON_SCHEMA`, `CHARACTER_INPUT_JSON_SCHEMA`, `CHARACTER_SNAPSHOT_JSON_SCHEMA`: request side, `io: 'input'`, draft-07), computed once from shapes that stay private to `character.ts`; never convert the guarded schemas, whose prototype-key pipe has no JSON Schema form.

**Nested objects are open.** zod parses the keys above with `looseObject` at every object level (`relations[]`, `origin`, `lives[]` and `lives[].death`, `venture`, `novels[]`, `sections`), never `z.object`, which strips unknown keys by default; the route schemas declare nested values loosely for the same reason (R-06). A round-trip test runs four real records through `POST`, `GET`, `GET .../versions` and the export with deep equality: one from `archpack.js`, one with `venture.missions`, `log`, `medals`, one with `novels[]` and `origin.env: 'romanzo'`, one with `lives[].death` (review I2).

**Pending relations** (`archui.js:85-88`). After an editor save the legacy resolves every character's pending relations and saves them in place (`archui.js:307`); after an import it resolves them in memory only, without a save (`archui.js:249`), so `updated` is not refreshed. The port writes the post-import resolution as in-place updates that keep `updated` unchanged, so the links survive a reload while the skip rule compares the same strings as in the legacy; the persistence is a parity row (review M7).

**Validation rules.**
- Any key `__proto__`, `constructor` or `prototype`, at any depth of an imported document, is refused before any processing (FR-013, edge cases), by a recursive check that runs before zod parses, so that zod never sees a poisoned object.
- An imported archive is validated with zod before any write (FR-046); a refused file writes nothing.
- The 200,000-character file cap, the 20,000-character section cap and the 12-item caps belong to `archParse` only (FR-014, edge cases).

**Ids (FR-017).** `LEGACY_ID_NAMESPACE` is `f0338bcd-0d4a-461e-9b1f-5c8a0414a6bc`, generated once. It is data, not configuration: every imported legacy id in both forms derives from it, so changing it would give the same file new ids on the next import. Never change it; `ids.test.ts` pins it. `mapIncomingId(id, newId)`: a uuid is kept; a non-empty non-uuid string becomes `v5(id, LEGACY_ID_NAMESPACE)` with `legacyId = id`; missing, empty or `null` gets `newId()` (the empty and `null` cases are a v1 deviation with a parity row). One id map per import is applied to every `id` and every relation `to`, snapshots included. The export writes `legacyId` when present, else the uuid, for ids and relation targets.

## State transitions

```text
                 versioned save (reason stored)      in-place update (no row, version kept)
                 +-----------------------------+     +----------------------------------+
                 v                             |     v                                  |
 (none) --first save, version 1, no reason--> CURRENT(version n, revision r) ------------+
                                               |  ^
                         soft delete (FR-023)  |  |  pack or import over the archived row:
                                               v  |  new version, reason 'pacchetto' or 'import archivio'
                                            ARCHIVED (archived_at set; hidden everywhere)
```

- **First save** (`creazione`, pack, seed, import of a new character): `version = 1` (or the incoming version for imports, as `Object.assign(archBlank(), c)` keeps it, `archui.js:249`), `revision = 1`, no history row, no reason stored (FR-016). Inline `versions` of a new character become history rows keeping `why` and `at` (edge cases).
- **Versioned save**: the current row's `(version, data)` becomes a `character_versions` row with the new save's reason; `version = old + 1`; `revision + 1`; retention applied. Over a stored character, inline versions in the file are discarded (edge cases, `archui.js:37, 249`).
- **In-place update** (relation cleanup, symmetric relations, pending resolution, and from WI-2 the game writes, P-03): `data` changes, `revision + 1`, `version` unchanged, no row.
- **Versioned save over an archived row** (the pack, FR-024; an import, FR-017): `archived_at` is cleared in the same write, and the archived version enters the history with reason `pacchetto` or `import archivio`.
- **Soft delete**: `archived_at = now()`, `revision + 1`; relations pointing to it are removed from the others as in-place updates in the same batch (FR-023, `archui.js:294`).
- **Restore of version N** (`archui.js:293`): a versioned save whose data is N's snapshot, reason `ripristino vN`.
- **Status and flags** inside `data`: `status` moves `vivo -> deceduto` (WI-2 game writes); `disabled` toggles through the editor's «⏸ Disattivato» checkbox, so it is a versioned save with reason «modifica manuale» (`archui.js:271, 297`), and a disabled character is hidden from game choices (`archui.js:165`, US1 scenario 8). The four legacy filters read these exactly as `archui.js:232` does: `vivi` = `!disabled && status !== 'deceduto'`, `deceduti` = `!disabled && status === 'deceduto'`, `disattivati` = `disabled`, `tutti` = every non-archived row. The counter of `archui.js:231` is not the same partition: its «vivi» is all rows minus the deceased, disabled ones included, and «disattivati» appears only when non-zero; both are ported verbatim with a test that pins the difference.
- **Every write** checks the expected revision; a stale one throws `StaleWriteError` and the whole batch is refused (P-03, FR-022, R-18).

## Batch (P-03, `CharacterStore.apply`)

```ts
type CharacterWrite =
  | { kind: 'versionedSave'; character: Character; expectedRevision: number | null; reason: string | null; inlineVersions?: VersionRow[] }
  | { kind: 'inPlaceUpdate'; character: Character; expectedRevision: number }
  | { kind: 'softDelete'; id: string; expectedRevision: number };
type CharacterBatch = readonly CharacterWrite[];
```

`expectedRevision: null` means "must not exist yet" (a first save); a first save whose id exists, or whose id is archived, is a conflict, and the planners turn the archived case into a versioned save (FR-017, FR-024). `PgCharacterStore.apply` runs the batch in one transaction: each write is a conditional `UPDATE ... WHERE id = $1 AND revision = $2` or an `INSERT`; a row count of 0, or a unique violation on `characters_pkey`, rolls back and throws `StaleWriteError`; any other constraint violation rolls back and surfaces as `internal`, so a data defect is never shown to the player as a conflict (review I6). The store never sets the record's `updated`: the planners set it from the injected `Clock` exactly where the legacy `archSave` does (`archui.js:38`), which is what lets the post-import pending resolution keep it.

## IndexedDB layout (`IndexedDbStore`, FR-051)

Database `unscripted`, version 1 (never the legacy `esperimento`, `archui.js:22`):

| Object store | Key | Value |
|---|---|---|
| `characters` | `id`, index `bySeq` on `seq` | `{ id, legacyId, version, revision, seq, data, archivedAt }` (same split as the table; `seq` is the next value after the last one of `bySeq`, read inside the `readwrite` transaction of the insert) |
| `characterVersions` | `[characterId, version]`, index `byCharacter` on `characterId` | `{ characterId, version, versionAt, reason, data }` |

`apply` runs in one `readwrite` transaction over both stores; it reads each touched record's revision inside that transaction before writing, and aborts the transaction with `StaleWriteError` on a mismatch (FR-051). Retention is applied in the same transaction. When `indexedDB` is missing or `open` fails, the store throws `StoreUnavailableError` (a core error class beside `StaleWriteError`) and the UI says the archive cannot be saved (edge cases; no localStorage fallback, a parity row).
